# @oxth/nestjs-otel — Plan 3: BullMQ Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** In an app using BullMQ, with or without `@nestjs/bullmq`, a job added inside a request shows up in the same trace: `POST /jobs` → `add emails` → `process emails` → `EmailsProcessor.process`. A failed attempt carries the stack trace, the attempt number and the redacted job data. Job metrics are exported. An idle worker records nothing.

**Architecture:**
- BullMQ (5.24 and later) already routes producer and consumer work through a pluggable `Telemetry` interface (`opts.telemetry`). That interface does nothing unless the app passes an adapter such as `bullmq-otel`.
- The library ships its own adapter, `getBullmqTelemetry()`, and a `BullmqInstrumentation` (the same `InstrumentationBase` pattern as Plan 2's ORMs). The instrumentation gives every `Queue`/`Worker`/`FlowProducer` the adapter when the app hasn't set one.
- BullMQ then does the context propagation itself, in its own wire format: a JSON W3C carrier in the job options, the same as `bullmq-otel`. Services using `bullmq-otel` and services using this library therefore join the same traces.
- The adapter records only producer operations and `process`. Every internal operation (polling, lock renewal, stalled checks, admin calls) runs with tracing suppressed.
- A wrapper around `Worker.prototype.callProcessJob` records errors, attempts, job data on failure, and metrics. It does this whoever supplied the telemetry.

**Tech Stack:** existing stack, plus `bullmq` `>=5.24.0 <7` (dev 6.5.x, `ioredis` peer), `bullmq-otel` 2.x (dev only, interop test), `@nestjs/bullmq` (fixture), and `redis:8` via testcontainers.

**Spec:** `docs/superpowers/specs/2026-10-28-nestjs-otel-design.md`: §5.4 (job data redaction), §5.5 (BullMQ metrics), §6 (BullMQ row: inject on `add`/`addBulk`/`FlowProducer`, extract in `Worker`, child-or-link, attempts and failures with stack). Plans 1 and 2 are merged on `main`. Read `README.md` and `src/` for current names, `src/orm/typeorm.ts` for the instrumentation pattern, and `src/orm/orm-span.ts` for error and parameter capture.

## Global Constraints

- All Plan 1 and Plan 2 Global Constraints still apply:
  - Telemetry never throws into app code (`safely`).
  - Scope name `@oxth/nestjs-otel`.
  - Config comes only from standard env vars.
  - The censor is `[REDACTED]`.
  - An instrumentation applies only within its version range and does nothing outside it.
- **Supported versions:** `bullmq >=5.24.0 <7` (optional peer dependency). The instrumentation name is `bullmq`; it is detected through the `bullmq` package.
- **The app's own telemetry wins.** If `opts.telemetry` is set on a `Queue`/`Worker`/`FlowProducer` (for example `BullModule.forRoot({ telemetry: new BullMQOtel() })`), the library never replaces it.
- **Recorded operations:** `add`, `addBulk`, `addFlow`, `addBulkFlows`, `addNode` (all `messaging.operation.type = 'send'`) and `process` (`'process'`).
  - Every other BullMQ operation gets no span and runs under `suppressTracing`.
  - Exception: `process` always starts from an unsuppressed context (`unsuppressTracing`), so a worker loop that happens to run under a suppressed context still records its jobs.
- **Span shape:**
  - Name: `${operation} ${queueName}` (for example `add emails`, `process emails`, `addFlow parents`), or just `${operation}` when BullMQ gives no queue name (`addBulkFlows`).
  - The kind is the one BullMQ passes (PRODUCER / CONSUMER).
  - Attributes: `messaging.system = 'bullmq'`, `messaging.operation.name = operation`, `messaging.operation.type`, `messaging.destination.name = queueName`, `messaging.message.id = job id`, and `messaging.batch.message_count` (from `bullmq.job.bulk.count`).
- **Parent:** the `process` span is a **child** of the producer span (BullMQ's behaviour). Retried attempts stay in the producer's trace.
- **Attribute allowlist:** only these BullMQ attributes are forwarded: `bullmq.queue.name`, `bullmq.queue.operation`, `bullmq.job.name`, `bullmq.job.id`, `bullmq.job.bulk.count`, `bullmq.job.bulk.names`, `bullmq.job.attempts.made`, `bullmq.worker.id`, `bullmq.worker.name`, `bullmq.flow.name`, `bullmq.job.scheduler.id`, `bullmq.job.type`, `bullmq.job.state`, `bullmq.job.processed.timestamp`, `bullmq.job.attempt_finished_timestamp`, and `bullmq.job.failed.reason` (passed through `redactString`).
  - Everything else is dropped. That includes `bullmq.job.result`, `bullmq.job.options`, `bullmq.queue.options`, `bullmq.worker.options`, `bullmq.job.key`, `bullmq.job.deduplication.key` and `bullmq.job.progress`.
  - Event attributes go through the same allowlist; event names are kept.
- **Attempt attributes on the `process` span:**
  - `bullmq.job.attempt` = `attemptsMade + 1`.
  - `bullmq.job.attempts.max` = `opts.attempts ?? 1`.
  - `bullmq.job.outcome`: one of `completed`, `failed`, `delayed`, `waiting`, `waiting-children`, `rate-limited`.
  - On failure: `bullmq.job.will_retry` (boolean).
- **Control-flow errors are not errors:**
  - These outcomes set only `bullmq.job.outcome`: `DelayedError` → `delayed`, `WaitingError` → `waiting`, `WaitingChildrenError` → `waiting-children`, and `RateLimitError` or a message of `bullmq:rateLimitExceeded` → `rate-limited`. Matching is by `err.name`.
  - They record no error status, no exception event and no failure metric.
- **Failure:**
  - `recordError(activeSpan, err, getClassifyDefaults())`. The innermost Nest span (for example `EmailsProcessor.process`) already carries the exception event, so the `process` span gets the ERROR status only (Plan 1 dedupe).
  - `will_retry = err.name !== 'UnrecoverableError' && attempt < max`.
- **Job data:**
  - Attribute `bullmq.job.data`: `serializeBody(getDefaultRedactor().redact(job.data), maxDataBytes)`, plus `bullmq.job.data.truncated = true` when cut. Set on the `process` span only.
  - Options: `OtelModule.forRoot({ bullmq: { captureData, maxDataBytes } })`. `captureData` is `'error' | 'always' | 'never'`, default `'error'`. `maxDataBytes` defaults to `8192` (`DEFAULT_MAX_BODY_BYTES`).
  - Job return values are never recorded.
- **Metrics:** meter `@oxth/nestjs-otel`.
  - Base attributes: `messaging.system`, `messaging.destination.name`, `messaging.operation.name = 'process'`, `bullmq.job.name`.
  - Instruments:
    - `bullmq.jobs.completed` counter.
    - `bullmq.jobs.failed` counter (+ `bullmq.job.will_retry`).
    - `messaging.process.duration` histogram, unit `s`, the processor time only (+ `error.type` = error class name, on failure).
    - `bullmq.job.wait_time` histogram, unit `s`, first attempt only (`attemptsMade === 0`). Value: `max(0, (job.processedOn ?? Date.now()) - (job.timestamp + (job.delay ?? 0))) / 1000`.
  - **Skipped** when the worker's `opts.telemetry` has a `meter` and is not the library's adapter, because BullMQ then emits its own `bullmq.jobs.*`.

## Review Focus

1. **An idle worker** (polling with `getNextJob`, lock extension, stalled checks every `stalledInterval`) must record zero spans. Otherwise every backend fills with one-span traces. Test: Task 3 `idle worker records no spans`.
2. **A secret in job data or in the job's return value** must never reach an exported span when the job succeeds, and must show only as `[REDACTED]` when it fails. BullMQ itself would put the result in the `job completed` event. Test: Task 3 `secret never leaks on success` and `failure: error with stack, redacted data, attempts`.
3. **An app that configures `bullmq-otel` itself** gets BullMQ's spans exactly once, with no second copy from the library, and its traces still connect to services using the library. Test: Task 3 `app-supplied telemetry is respected and interoperates`.
4. **A worker created inside a span** (for example inside a request handler, or under `onModuleInit` tracing) must not parent every job to that span. Test: Task 3 `worker created inside a span does not adopt it`.
5. **Retries:** each attempt gets its own `process` span in the producer's trace, with the right attempt number, and `will_retry=false` on the last attempt. Test: Task 3 `failure: error with stack, redacted data, attempts`.
